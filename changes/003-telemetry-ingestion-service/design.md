# Design — Change 003: telemetry-ingestion-service

> **Technical decisions, trade-offs, and how the spec is realized in code.**

---

## 1. Build system

`pom.xml` depends on:

- `spring-boot-starter-web` — required transitively by actuator;
  removed at runtime if no REST endpoints are exposed (the service
  has none in this change).
- `spring-boot-starter-actuator` — health probes.
- `spring-kafka` — `@KafkaListener` and `KafkaTemplate`.
- `spring-boot-starter-data-jpa` — JPA + Hibernate.
- `spring-boot-starter-data-redis` — `StringRedisTemplate` for the
  latest-state cache.
- `spring-boot-starter-validation` — for DTO deserialization (JSON
  side).
- `org.postgresql:postgresql` (runtime) and `com.h2database:h2`
  (runtime + test).
- `spring-kafka-test` (test) — provides `@EmbeddedKafka`.

> The testcontainers path documented in the original spec is
> replaced by `@EmbeddedKafka` (faster, no Docker required) and H2
> (already in test scope). Testcontainers is a follow-up — see §6.

## 3. Domain layer (no Spring / JPA / Kafka / Redis)

- `TelemetryPayload` — pure POJO with the four top-level fields.
- `GpsCoordinates` — `(latitude, longitude)`.
- `TelemetryMetrics` — `(engineTemp, rpm, fuelLevel, speed)`.

These types are the *contract* of the platform. Renames require a
spec update.

## 4. Use case

`ProcessTelemetryUseCase.execute(payload)` does:

1. Save to Redis (latest state).
2. Persist to JPA (history).
3. Republish to `agri.telemetry.processed` via the Kafka producer.

Each step is independent; the use case logs and continues on
infrastructure errors (matching the spec's degraded-mode rules).

## 5. Infrastructure

### 5.1 `TelemetryConsumer`

```java
@KafkaListener(topics = "agri.telemetry.raw", groupId = "telemetry-ingestion-group")
public void consume(String message) { ... }
```

Catches `JsonProcessingException` for malformed payloads and
rethrows for Kafka redelivery. Other exceptions propagate as well,
so the standard `DefaultErrorHandler` (auto-configured by Spring
Kafka) handles re-delivery.

### 5.2 `TelemetryProducer`

`KafkaTemplate<String, String>` serialises the same `TelemetryPayload`
JSON to `agri.telemetry.processed` using the equipment id as the
message key (ensures per-equipment ordering for downstream consumers).

### 5.3 `LatestStateRepository`

`StringRedisTemplate` writes the JSON serialisation of
`TelemetryPayload` to `telemetry:latest:<equipmentId>`.

### 5.4 JPA layer

- `TelemetryEntity` — `@Entity` mapped to `telemetry.telemetry_events`
  with columns:
  - `id`              BIGINT (autogenerated PK)
  - `equipment_id`    VARCHAR(64)   NOT NULL
  - `event_timestamp` TIMESTAMP WITH TIME ZONE NOT NULL
  - `latitude`        DOUBLE PRECISION
  - `longitude`       DOUBLE PRECISION
  - `engine_temp`     DOUBLE PRECISION
  - `rpm`             INTEGER
  - `fuel_level`      DOUBLE PRECISION
  - `speed`           DOUBLE PRECISION
  - `created_at`      TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now()
- `TelemetryJpaRepository extends JpaRepository<TelemetryEntity, Long>`.

The entity has a no-arg constructor for JPA plus the full-args
constructor used by the use case.

## 6. Configuration profiles

`application.yml` declares:

- **default** — uses H2 (in-memory) and embedded broker settings
  (active only with `@EmbeddedKafka`). Useful for local dev with
  no infra.
- **docker** — points to the real PostgreSQL + Redis + Kafka on the
  compose network. Activated by `SPRING_PROFILES_ACTIVE=docker`.
- **test** — H2 in-memory + `@EmbeddedKafka` for the consumer test.

## 7. Testing strategy

- **`ProcessTelemetryUseCaseTest`** — unit, mocks the Redis repo,
  JPA repo, and the producer. Three cases.
- **`TelemetryConsumerTest`** — `@SpringBootTest` +
  `@EmbeddedKafka` produces a real `agri.telemetry.raw` message
  and asserts the use case ran (via a Mockito `@MockBean`).
